# Пошаговая настройка VPS

Статус: согласовано пользователем; реализация и выпуск поручены агенту.

## Цель

Разделить обычное подключение и настройку VPS. Пользователь понимает каждое изменение и может отказаться от ненужных действий. Используем существующий CLI и механизм ключей телефона и резервного доступа, без новых зависимостей.

## Вход в мастер

- «Серверы → Добавить сервер» открывает два варианта: «Подключить существующий сервер» и «Настроить новый VPS».
- Первый вариант сохраняет существующий сценарий добавления без системной настройки.
- «Серверы → Список серверов → выбранный сервер → Настроить VPS» запускает тот же мастер с заполненными адресом, портом и исходным логином.
- В «Действиях на сервере» также доступен пункт «Настроить VPS» (из первоначального запроса).
- Отдельный дублирующий пункт «Новый VPS: настроить с нуля» в разделе серверов заменяется этим входом.
- Сохраняем ограничение текущего приложения: мастер настройки доступен владельцу резервного доступа, не участникам команды.

## Шаги

Каждое пользовательское изменение имеет отдельный вопрос «Выполнить / Пропустить» с объяснением пользы и последствий. Выбор собирается до изменений, затем показывается полный план и запрашивается подтверждение. Технические проверки, резервные копии, установка прав файлов и необходимый перезапуск входят в выбранное действие, не выдаются за отдельные необязательные команды.

1. Обновить список пакетов (`apt update`): не устанавливает обновления пакетов.
2. Создать отдельного пользователя: запросить логин; не использовать root. Можно пропустить и продолжить с текущим пользователем. Существующий чужой логин не переиспользуется молча: отказ с предложением другого имени.
3. Выдать целевому пользователю права администратора (`sudo`): отдельный вопрос, по умолчанию предложено. Пароль для sudo вводится в SSH-терминале и нигде не сохраняется. Если sudo не выбирается, новый пользователь остаётся обычным; настройка системы выполняется через исходную привилегированную учётную запись, а не требует sudo у нового пользователя.
4. Настроить цвета терминала: добавить `export TERM=xterm-256color` в `~/.profile` целевого пользователя без дублирования. Настройка применяется для следующих входов; никакой бессмысленной отдельной команды `export` в кратком удалённом сеансе.
5. Настроить вход ключами приложения для целевого пользователя: публичный ключ телефона и резервный ключ, не удаляя остальные ключи. Приватный ключ на VPS не генерируется. Отказ допустим, но новое подключение не объявляется рабочим без успешной проверки входа ключом.
6. Изменить порт SSH: запросить порт; при пропуске оставить текущий.
7. Запретить SSH-вход под root: отдельный выбор.
8. Отключить парольный вход по SSH: отдельный выбор; объяснить, что отключается также интерактивный пароль, но не пароль для sudo.

Решение разработчика: все изменения предлагаются, но ни одно не выполняется без явного выбора и итогового подтверждения. Не добавляем установку пакетов, полное обновление ОС, удаление пользователей, отзыв старых ключей или passwordless sudo.

## Доступ и безопасность

- Системная настройка по-прежнему поддерживает Ubuntu/Debian; остальные системы получают понятный отказ до изменений.
- Для незарегистрированного VPS использовать существующий выбор способа первого входа (пароль или имеющийся ключ). Для сохранённого подключения использовать вход телефоном, при отсутствии установленных ключей — существующий механизм первого входа.
- До выполнения проверить доступность, исходные права, поддержку SSH-конфигурации и зависимости выбранных шагов. Если нужна привилегия, которой нет, объяснить и не начинать привилегированную часть.
- Нельзя отключить root-вход, если целевой проверенный пользователь — root. Нельзя отключить пароли до успешного отдельного входа ключом. При невозможной комбинации предложить изменить план или отменить, а не самовольно добавлять шаги.
- Смена порта сначала оставляет старый порт и доступ. Проверяется новый вход в отдельном SSH-соединении. Закрытие старого порта и ограничения входа — только после проверки.
- Менять SSH через отдельную управляемую конфигурацию, учитывая приоритет относительно cloud-init, проверяя `sshd -t` и эффективные параметры. Не редактировать через nano и не перезаписывать чужие настройки без копии.
- Перед изменением SSH сохранить исходные настройки этого запуска и поставить независимый откат через 3 минуты. При неуспехе нового входа восстановить именно состояние перед запуском, а не настройки предыдущего мастера. После успешного нового входа отменить откат. Повторный запуск не должен затереть чужой ожидающий откат.
- Учитывать `ssh.socket` и обычный ssh/sshd service, активный UFW. Предупредить, что внешний firewall хостера может требовать ручного открытия порта. При ошибках не сообщать, что сервер точно не изменён.
- Опасные действия требуют подтверждения телефона существующим механизмом. Секреты не включаются в состояние, сообщения или отчёты.

## Записи подключений

- После установки ключей сохранить целевое подключение на телефоне и ПК существующим механизмом; до успешной проверки оно имеет пометку непроверенного/незавершённого подключения.
- При новом логине или порте создать отдельную запись, не затирать исходную автоматически. Если целевая запись уже есть, избежать дубликата и подтвердить её изменение.
- После успешного финального входа предложить «Удалить старое подключение из списка?», по умолчанию нет. Это удаление только записи с синхронизацией ПК и телефона: не удаление пользователя, файлов или ключей на VPS.
- Если исходная и целевая запись совпадают, не предлагать удалить единственное рабочее подключение. При сбое сохранения или проверки исходную запись не удалять.
- Итог перечисляет выполненные, пропущенные и неудачные шаги, рабочее подключение и состояние отката. Частичный успех не называется полным успехом.

## Проверка и границы

Добавить тесты выбора и зависимостей шагов, отсутствия команд пропущенных действий, имён/портов и shell-экранирования, обоих входов в мастер, прав sudo, сохранения ключей, порядка проверки/ограничений, точного отката, повторного запуска, синхронизации и отказа от удаления старой записи. Использовать существующие тесты и shell-песочницу, не менять реальные VPS.

Обновить русские и английские строки/инструкции, версию приложения (для обновления телефона) и встроенную Nix-копию, если она требуется устройством репозитория. Прогнать существующие тесты. Реальная проверка Android/VPS остаётся отдельной: не выдавать тесты с заглушками за доказательство отсутствия риска потери доступа.
